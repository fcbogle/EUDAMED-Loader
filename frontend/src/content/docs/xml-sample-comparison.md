# XML Sample Comparison

## Purpose

This note compares two colleague-provided single-record XML samples against the equivalent XML output generated by this application.

The current intent is not to produce an exhaustive diff. It is to highlight only material differences that may indicate:

- a structural XML design difference
- a semantic difference in `POST` / `PATCH` handling
- a likely schema-validity issue
- a potentially incorrect business interpretation

Minor content omissions are not treated as major findings here unless they affect XML meaning or validity.

## Comparison Scope

Colleague samples reviewed:

- `Echelon_UDI_DI_POST 1.xml`
- `Echelon_UDI_DI_PATCH 1.xml`

Equivalent records in this system:

- `EC22L1SD`
- `EC22L1S`

Stored project XML artifacts for ongoing review are kept in:

- `docs/xml_samples/`

## High-Level Findings

The two systems are not using the same XML design approach.

The colleague samples model the payload as a single `device:UDIDIData` element, while this application models the payload as a `device:Device` wrapper containing:

- `device:MDRBasicUDI`
- `device:MDRUDIDIData`

This is not a minor content difference. It is a structural modeling difference.

The most significant current issue is that the colleague `POST` sample for `EC22L1SD` does not match the current operational classification in this system, which treats `EC22L1SD` as `PATCH`.

At present, the most likely explanation is not that this application failed to locate the equivalent record. The record identity aligns closely across both systems, which suggests the colleague sample was created as a `POST` example even though the current authoritative operational classification for that record appears to be `PATCH`.

## Significant Findings

### 1. `EC22L1SD` Operation Semantics Do Not Match

For `EC22L1SD`:

- colleague sample:
  - `serviceOperation = POST`
- this system:
  - `serviceOperation = PATCH`

This is a significant difference because it changes the submission meaning, not just the content payload.

The current evidence suggests this is more likely to be a sample-construction difference than a record-matching failure in this application:

- `referenceNumber` matches
- device identifier `DICode` matches
- Basic UDI identifier matches

That means the two XMLs appear to represent the same device record, but with different operation semantics applied to it.

The most likely interpretation is that the colleague sample was prepared as a simplified `POST` example, while the current source-controlled operation in this application resolves the same record as `PATCH`.

This should still be reviewed with QMS or against current EUDAMED registration reality before treating the two XMLs as equivalent.

### 2. Payload Structure Is Materially Different

Colleague samples use:

- `device:UDIDIData`

This system uses:

- `device:Device`
  - `device:MDRBasicUDI`
  - `device:MDRUDIDIData`

This is a significant architectural difference.

It may reflect:

- a different schema interpretation
- a different schema version
- or a simpler XML design that does not model the full object structure this application currently emits

This difference should not be treated as a simple “more or less populated” payload difference.

### 3. `serviceID` Value Does Not Match

Colleague samples use:

- `serviceID = UDI_DI`

This system uses:

- `serviceID = DEVICE`

Because `serviceID` is part of the service wrapper, this is a potentially significant interoperability difference and should be checked against the correct EUDAMED service contract for the current message type.

### 4. `productionIdentifier` Interpretation Differs

Colleague samples use:

- `SERIALISATION_NUMBER MANUFACTURING_DATE`

This system uses:

- `SERIALISATION_NUMBER`

In the local schema set used by this application, the colleague-style combined value would not be valid as the current XML enum representation.

This is therefore a potentially significant schema-validity difference, not just a content choice.

### 5. `numberOfReuses` Semantics Differ

Colleague samples use:

- `-1`

This system previously used:

- `1`

The current application now aligns this non-applicable case to:

- `-1`

This is potentially significant because it suggests a different interpretation of the underlying workbook logic rather than a simple missing field.

This should be checked against the intended business rule for the current Echelon records.

### 6. `PATCH` Version/State Handling Differs

For the colleague `PATCH` sample:

- `e:version = 2`
- `e:state = REGISTERED`

In the current XML generated by this system for the equivalent `PATCH` sample:

- no `e:version`
- no `e:state`

This is potentially significant if those fields are required or expected for update semantics in the actual EUDAMED object lifecycle.

This should be confirmed against the correct schema/design rules for `PATCH`.

## Non-Material Differences

The following differences are not currently treated as major issues:

- runtime metadata:
  - `messageID`
  - `correlationID`
  - `creationDateTime`
- broader content population in this system where the colleague sample is simply leaner
- market information count differences where this system is projecting the fuller canonical market-availability dataset

For example, the current application emits `25` `marketInfo` entries while the colleague samples emit `1`. This is treated here as a design/content-scope difference rather than a major problem by itself.

## Current Positive Alignment

The following values align cleanly between the two systems for the equivalent records:

- `referenceNumber`
- device identifier `DICode`
- Basic UDI identifier `DICode`
- trade-name direction appears broadly consistent

That means the two systems are not fundamentally disconnected. The main differences are at the level of:

- operation semantics
- wrapper/service modeling
- selected XML field semantics

## Recommended Next Review Questions

Before using the colleague samples as a benchmark, the following should be clarified:

1. Should `EC22L1SD` currently be `POST` or `PATCH`?
2. Is the service wrapper expected to use `UDI_DI` or `DEVICE`?
3. Should the payload root be `device:UDIDIData` directly, or a fuller `device:Device` structure?
4. Is `productionIdentifier` expected to support a combined value, or should it resolve to a single enum token?
5. Should `PATCH` samples carry explicit `state` and `version` values?

These questions should be settled before judging one XML design as definitively correct.

## Device.xsd Versus UDIDIData Discussion

The XML comparison also raises three broader design questions that should be settled before the submission-layer XML design is treated as final:

1. What is the intended business object for this submission?
   - a fuller device object
   - or UDI-DI registration data only

2. What does the intended EUDAMED message/schema expect as the payload root?
   - `device:Device`
   - or `device:UDIDIData`

3. Is `MDRBasicUDI` supposed to travel in the same payload for this use case?
   - this application currently assumes yes
   - the colleague sample suggests no, or at least not in the same structure

These questions are separate from simple field population. They determine which XML design approach is actually correct.

## Official EUDAMED Signals

Public EUDAMED documentation gives useful signals on the XML design, even though it does not fully publish the exact wrapper contract in a way that settles every question.

### Device Upload Object Signal

The strongest official signal comes from the UDI/Device Business Rules for data exchange upload.

The rules state that a **Device upload object** should contain:

- Basic UDI / EUDAMED DI information
- optional certificate and clinical-investigation links
- UDI-DI / EUDAMED ID information
- optional market information
- optional product designer information
- optional package information

This points toward a fuller **Device-oriented upload object** rather than a bare standalone `UDIDIData` payload.

In other words, the public rules are directionally closer to this application's current `Device`-oriented design than to the colleague sample's simpler `UDIDIData`-only design.

### Basic UDI And UDI-DI In The Same Submission Context

The public UDI/Devices module overview also describes Regulation-device registration in two linked levels:

- Basic UDI-DI level
- UDI-DI level

and notes that a new Basic UDI-DI registration is associated with one UDI-DI/Device.

This supports the idea that Basic UDI information and UDI-DI information belong to the same upload object context for regulation-device registration.

### Service Analysis

The XML comparison also revealed a service-layer difference:

- colleague sample:
  - `serviceID = UDI_DI`
- this application:
  - `serviceID = DEVICE`

Public EUDAMED material available online strongly supports a **UDI/Device module** and a **Device upload object**, but it does **not** provide a sufficiently explicit public technical statement to prove whether the exact service wrapper should use:

- `DEVICE`
- or `UDI_DI`

So the current position is:

- the **module/service domain** is clearly UDI/Device
- the **object design** appears to favor a Device-oriented upload object
- but the exact `serviceID` token still requires confirmation from the more detailed EUDAMED technical documentation or an authoritative working example

### PATCH State And Version Signal

Public business rules also indicate that:

- new submissions create versions
- submitted entities have states
- updates create new versions and state handling matters

This means the colleague sample's inclusion of `state` and `version` should not be dismissed as arbitrary. Even if the colleague XML structure is not the final benchmark, its update semantics are directionally consistent with public EUDAMED business-rule concepts and should be reviewed carefully.

### Current Interpretation

Based on the public material reviewed so far, the best current interpretation is:

- this application's **Device-oriented** XML design is better supported than a pure `UDIDIData`-only design
- the colleague sample still raises valid questions about:
  - exact `serviceID`
  - exact update semantics
  - whether explicit `state` and `version` should be present in `PATCH`

So the public evidence currently supports the broader design direction of this application more than the colleague sample, while still leaving important service-wrapper and update-semantics questions open.

## EUDAMED Discussion Checklist

If there is an opportunity to discuss transport and submission design directly with EUDAMED or through QMS, the following questions should be prioritized.

### XML Contract

1. For UDI/Device M2M submission, what is the correct service wrapper contract?
   - exact `serviceID`
   - exact payload root
   - exact `POST` versus `PATCH` expectations

2. For `PATCH`, are `state` and `version` required in the payload, or are they managed implicitly by EUDAMED?

3. Is a regulation-device upload expected to be a fuller Device object including Basic UDI and UDI-DI context, or can it be a narrower `UDIDIData` submission?

4. Are official XML examples available for:
   - one regulation-device `POST`
   - one regulation-device `PATCH`
   - one batch upload

### M2M / AS4 / eDelivery

5. Is the expected transport pattern standard eDelivery `AS4` with Domibus-compatible access points?

6. What is the onboarding sequence for a manufacturer or producer?
   - registration
   - endpoint exchange
   - certificates
   - test environment access
   - production approval

7. What certificates are required?
   - TLS/server
   - signing
   - encryption
   - approval/issuance expectations

8. What AS4 message settings are expected?
   - PMode ownership
   - retry policy
   - receipts / acknowledgements
   - payload size limits
   - compression expectations

### Submission Semantics

9. What constitutes the business identifier for replay/idempotency?
   - `messageID`
   - `correlationID`
   - device identifiers
   - version

10. How should the application distinguish:
    - new registration
    - update to existing version
    - correction
    - discard / logical delete

11. Are there message-ordering rules?
    - actor registration before device upload
    - Basic UDI before UDI-DI
    - certificate dependencies before submission

12. If one record in a batch fails, does EUDAMED reject:
    - the whole batch
    - only the failed entity
    - or return partial acceptance

### Responses And Error Handling

13. What response artifacts should the application persist?
    - AS4 receipt
    - technical acknowledgement
    - business acknowledgement
    - per-entity validation result

14. Are stable machine-readable rejection/error codes available for:
    - schema rejection
    - business-rule rejection
    - duplicate identifier
    - wrong operation
    - actor authorization failure

15. What is the expected retry strategy for:
    - transient transport failure
    - duplicate submission uncertainty
    - timeout after send with no business response

### Environment And Operations

16. Which environments are currently available for onboarding, testing, and production use?

17. What evidence is required before production access is granted?

18. Are upload quotas, throttling, or maintenance windows documented?

19. For lower-volume manufacturers, is the recommended path:
    - manual upload first
    - then M2M later

### Current Application Design Review

20. Does the current `DEVICE` service wrapper look directionally correct?

21. Is emitting the fuller repeated `marketInfos` structure correct for regulation-device upload?

22. For a current Echelon `PATCH` sample, what would EUDAMED expect that is missing today?
